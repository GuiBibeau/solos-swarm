# PR sequence

Six PRs. Each leaves `main` shippable, deletes what it replaces in the same change (nothing ships two ways), and ends in a behavior test that runs offline against the fake GitHub (`tests/support/fake_github.rs`, grown from the fake `tests/agent_github.rs` already holds) plus `file://` bare repositories through `github.git_base`, with the scripted harness and the real broker. No test calls GitHub or a model. Builds and tests run on the remote box. "Unedited" means an existing test passes without a change.

Each PR also adds one feature recipe to `.claude/skills/verify-agent-mode/features/` and runs it on remote-ai through `/verify-agent-mode` against `GuiBibeau/solos-swarm-sandbox`, a throwaway repository the owner controls, with a real DeepSeek Router and real Pi workers. The verify config lists only the sandbox in `forge.repos`, so every token a run mints is narrowed to the sandbox. A recipe's evidence is a side effect on GitHub the model could not invent, read on the Mac with `gh`.

Every PR that adds a Ticket field, an event, an Effect or a stored enum variant bumps the store schema with an empty migration, so an older build refuses the file: V7 in PR 2, V8 in PR 3 (`MessageKind::Status`), V9 in PR 5 (`Ask::Merge`, `Change.verdicts`, `Ticket.outsiders`).

**Tools added across all six PRs: none.** `extensions/agent-tools.json`, `tests/fixtures/agent-tools.json`, `extensions/broker.ts` and the registry are byte-unchanged in every PR. PR 2 adds `no_worker_tool_touches_the_forge`: a golden list of `WORKER_TOOLS`, so a future forge tool fails a test and sends its author back to this design.

This sequence supersedes PRs 3, 4 and 7 of [`../pstack/prs.md`](../pstack/prs.md) where they conflict. PRs 5 (delegates) and 6 (two families) are unchanged and may land anywhere after PR 2.

Order and dependencies:

- **1 → 2 is the first usable path.** After 1 the agent answers on GitHub as itself, and the owner can create the App from the manual list the day this design lands. After 2 a person gets a real pull request from a chat message or a GitHub mention.
- **3 needs 2** (it watches Changes). **4 needs 2** for review summaries (they are read on the bot's PRs); its label half needs only 1. **5 needs 3** (the gate reads observed CI, and verdicts come from `observe`).
- **6 can be pulled forward** to precede 1's live proof if the owner prefers `init` to the manual list.

Later, not scheduled:

- **The webhook delivery log as a second `EventFeed`.** `GET /app/hook/deliveries` on an active webhook whose URL cannot receive, read with the App's JWT: one cursor and typed events instead of five listings. It starts with a live spike on a throwaway App (retention, order, whether a hook that always fails stays active, payload shape), recorded in this directory. It replaces `RestFeed` only if the spike holds and polling has proved too slow or too costly; nothing else would change.
- Stacks (`Ticket.change` becomes a map); inline review-thread replies (`ChannelRef` gains `in_reply_to`); labels as the budget-approval gesture on GitHub; a host-run gate command inside `admit` (the pstack `check`, as config rather than a tool); a second-family review as one more `Waiting` reason; adopting a collaborator's push instead of parking the Change.
