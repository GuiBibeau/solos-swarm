# PR sequence

The [Amendments](rationale.md#amendments) apply to every PR below, each folded into the PR that owns the file it changes.

PRs 3, 4 and 7 below are superseded by [`../github-app/prs.md`](../github-app/prs.md) where they conflict.

Each PR can be checked by itself, leaves `main` shippable, and ends in a behavior test that runs offline: the scripted harness against the real broker, a fake upstream, and `LocalForge` (a bare repository and a JSON file of pull requests on disk). Builds and tests run on the remote box, never on the Mac. "Unedited" means an existing test passes without a change.

Each PR also adds one feature recipe to `.claude/skills/verify-agent-mode/features/` and runs it on remote-ai through `/verify-agent-mode`, with a real DeepSeek Router and real Pi workers, driven through `mcp.sh` as a person would. That recipe is the live proof. Its evidence must hold a side effect the model could not invent, per that skill's proof standard. Publishing recipes use a sandbox repository the operator owns (named `GuiBibeau/solos-swarm-sandbox` below), never solos-swarm itself, until PR 7. Keeping the recipes current is `/pstack:maintain-verification-skill`'s job.

Every PR that adds a Ticket field, an Input kind or an event bumps the store's schema version with an empty migration, as V5 did, so an older build refuses the file instead of dropping what it cannot read.

Notes on PR 3:

- A worker writes the clone's `.git/config`, so when the host runs git to push, it treats that file as hostile. `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `credential.helper` and `url.*.insteadOf` each make git run a program or reach a host the worker chose, with the host's authority and, in a push, its token. The host never runs git in `work/`. It fetches the worker's commits from the clone into the host mirror, as a bundle made in the sandbox, with `fsckObjects`, and pushes from the mirror, whose config only the host writes. The token goes in the environment of the mirror's git alone, never in the clone's environment, its config or its argv.

Order and dependencies:

- **1 → 2 → 3 is the first usable path.** After 1, every session works the pstack way: questions, research and prose get poteto-mode, its playbooks and its principles. After 2, questions about a repository are answered from its real code. After 3, a person gets a real pull request from a chat message. Until 5, pstack's delegation steps take its own "subagent forbidden to spawn" path, which pstack supports as written.
- **4 makes 3 trustworthy.** It comes right after 3, so the window in which `ready` can report an unproven pull request is one PR wide and only on the sandbox repository.
- **5 and 6 bring fan-out and diversity.** 5 works with one family. 6 is config and credentials on top of it.
- **7 closes the loop** from request to merged change, and is the first PR whose live proof may touch solos-swarm itself.

Later, not scheduled:

- Delegates and repository Tickets on remote nodes (wire support for bundles and forks).
- Delegates of depth two, with one pool per depth so a waiter never holds the slot it waits for.
- Delegates on Claude Code, and a delegate browser with its own trail cursor.
- `thinking` per alias, and an effort mapping in the adapter.
- The CI watcher reporting new review threads, and pull-request review events from the github Source.
- A Goal "selected" artifact mode for Router-level fan-out over swarm mode.
